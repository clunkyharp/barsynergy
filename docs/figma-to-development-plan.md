# План переноса дизайна из Figma в разработку

Дата: 2026-05-23

Режим: `IMPLEMENTATION`

## Цель

Перенести визуальный язык макетов BARSYNERGY из Figma в рабочий Next.js-код без замены данных, маршрутов и бизнес-логики.

Перенос должен улучшить консистентность интерфейса: типографику, сетку, отступы, карточки, кнопки, метки, панели, формы и состояния. Это не задача на точное копирование каждого экрана из Figma.

## Жёсткие ограничения

Не трогать в рамках этого переноса:

- header;
- footer;
- логотип;
- иконки из Figma;
- структуру данных;
- Prisma schema и миграции;
- seed-данные;
- маршруты;
- server actions, API и права доступа;
- тексты и реальные CMS-записи без отдельного согласования;
- форму и состав публичных данных на страницах.

Фото и иллюстрации:

- не переносить изображения из Figma как источник истины;
- сначала использовать уже готовые локальные изображения по смыслу;
- если локального изображения не хватает, подобрать подходящее внешнее фото и зафиксировать источник;
- не использовать логотипы, иконки и брендовые графические элементы из Figma как файлы приложения без отдельного разрешения.

## Главный принцип

Переносим не «пиксель в пиксель», а дизайн-решения:

- визуальную иерархию;
- плотность интерфейса;
- роли поверхностей;
- типографические роли;
- характер карточек и списков;
- состояния кнопок, фильтров, форм и меток;
- поведение на настольном и мобильном экране без горизонтального переполнения.

Если layout в Figma конфликтует с реальными данными, побеждают данные и текущая информационная архитектура. Код должен адаптировать макет под живой контент, а не подгонять контент под картинку.

## Источники

Основной Figma-файл:

```txt
BARSYNERGY
file key: aKzJvpAdbGIdIhc7J3MQNv
```

Рабочие источники в репозитории:

- `DESIGN.md` - текущий дизайн-контракт приложения;
- `src/app/globals.css` - токены, темы, глобальные поверхности;
- `src/components/ui` - базовые UI-примитивы;
- `src/components/public` - публичные шаблоны и секции;
- `docs/ui-ux-design-refactor-plan.md` - исторический план UI/UX-ремонта;
- `docs/figma-runtime-transfer-map.md` - live-карта переноса Figma-узлов в код.

Figma Console MCP использовать как обязательный источник проверки, навигации по файлу и уточнения узлов. Если Figma API ограничен лимитом запросов или авторизацией, работу по новым визуальным решениям нужно ограничить уже полученными live-данными Desktop Bridge и явно записать этот gap в QA-отчёт. Локальные экспорты не использовать как источник решений по текущему переносу.

## Что считается переносом

Перенос засчитывается, когда экран или группа экранов:

- использует существующие данные из текущих серверных загрузчиков и actions;
- сохраняет текущий маршрут;
- сохраняет текущую роль страницы;
- выглядит как часть одной системы с Figma-макетами;
- не копирует header/footer, логотипы и Figma-иконки;
- проходит визуальную проверку на настольном и мобильном экране;
- не имеет горизонтального переполнения;
- не ломает проверки `lint` и `typecheck`.

## Что не считается переносом

Не считать переносом:

- вставку Figma-скриншота как фон;
- ручное создание отдельной страницы с фейковыми данными;
- замену живого каталога статичным layout из макета;
- изменение схемы данных ради совпадения с макетом;
- перенос логотипов, иконок или декоративных assets из Figma;
- локальную правку одной страницы, которая создаёт новый стиль вне общих UI-примитивов.

## Рабочий порядок

### 1. Инвентаризация

Для каждой группы макетов зафиксировать:

- live-узел Figma;
- какие маршруты приложения она покрывает;
- какие компоненты уже есть в коде;
- где есть расхождение;
- что переносим как визуальный принцип;
- что не переносим из-за данных, header/footer или ограничения по assets.

Результат этапа: короткая карта `Figma -> route/component`.

### 2. Контракт перед кодом

Перед реализацией группы экранов зафиксировать:

- целевые экраны;
- повторно используемые токены и компоненты;
- источник изображений;
- что не входит в работу;
- размеры экрана для проверки;
- критерии готовности.

Этот контракт нужен, чтобы не превратить перенос в широкий редизайн.

### 3. Сначала общие примитивы

Сначала переносить повторяемые роли:

- кнопки;
- chips/meta labels;
- cards/panels;
- public list rows;
- детальные шаблоны;
- filters;
- form fields;
- empty/filtered states;
- action blocks.

Страничные правки допустимы только если общий примитив уже не подходит или экран имеет уникальную роль.

### 4. Страницы группами

Работать небольшими группами:

1. Публичные каталоги и списки.
2. Публичные детальные шаблоны.
3. Публичные формы и фильтры.
4. Страницы входа и служебные публичные поверхности, если они есть в выбранной части Figma.
5. Админские и общие поверхности только отдельным пакетом работ и только после явного подтверждения.

Внутри группы не менять данные. Например, если Figma показывает другую карточку, а приложение получает CMS-запись из базы, сохраняем CMS-запись и переносим только визуальную форму карточки.

### 5. Адаптация под размеры экрана

Мобильный экран не должен быть механически сжатым настольным макетом.

Для мобильной версии допустимо:

- менять порядок блоков;
- объединять второстепенные панели;
- переносить длинные действия ниже;
- уменьшать hero;
- скрывать вторичную навигационную строку, если она дублирует смысл.

Недопустимо:

- обрезать реальные заголовки;
- уводить кнопки за видимую область экрана;
- делать горизонтальный скролл;
- прятать важные данные только ради сходства с Figma.

### 6. QA и фиксация расхождений

На каждый пакет работ:

- `git diff --check`;
- `npm run lint`;
- `npm run typecheck`;
- при затрагивании границы Prisma - `./node_modules/.bin/prisma validate`;
- визуальная проверка на настольном и мобильном экране;
- скриншоты или явная запись, почему скриншот невозможен.

Для визуальной проверки указывать фактический инструмент:

- built-in browser;
- Chrome DevTools Protocol;
- Playwright screenshot;
- быстрая проверка HTML/исходников, если браузер недоступен.

## Чеклист приёмки

Перед закрытием пакета работ:

- header/footer не изменены, если это не отдельная согласованная задача;
- данные, маршруты, загрузчики и actions не изменены без причины;
- Figma-иконки и логотип не перенесены;
- изображения взяты из локальных assets или из зафиксированного внешнего источника;
- layout адаптирован под реальные данные, а не скопирован слепо;
- общий стиль не расходится с `DESIGN.md`;
- нет новых разовых цветов, радиусов и теней без токена или общего примитива;
- настольный и мобильный экран проверены;
- нет горизонтального переполнения;
- команды проверки записаны в итоговом отчёте;
- решение по синхронизации документации и Kanban записано в итоговом отчёте.

## Риски

- Figma может показывать идеальный статичный контент, а приложение получает длинные русские заголовки, пустые состояния и разные наборы меток.
- Точный перенос layout может ухудшить UX, если на странице живые фильтры, формы или CMS-данные.
- Без общих примитивов перенос быстро распадётся на набор локальных стилей.
- Прямой Figma API может быть недоступен из-за авторизации или лимита запросов; в этом случае новые решения нельзя подменять локальными экспортами, нужно фиксировать ограничение и продолжать только в пределах уже полученных live-данных Figma Console MCP.

## Следующий практический шаг

Сделать карту Figma-макетов по текущим маршрутам приложения и отметить приоритеты:

- уже реализовано;
- нужно выровнять visually;
- не переносить из-за ограничения;
- нужно решение владельца.

После карты открывать отдельные пакеты реализации по одной группе экранов.
