# UX/UI Аудит и план исправлений — BARSYNERGY

> **Дата:** 2026-06-01
> **Версия:** feature/stabilization-remediation
> **Область:** публичный сайт, auth-флоу, бизнес-кабинет, админ-панель (login)
> **Ревьюер:** Claude Opus 4.6

---

## 1. Общая оценка

**Суммарная оценка: 6.5 / 10**

### Что сделано хорошо

- **Визуальная идентичность** — coffee-bar стилистика узнаваема: тёплые тона (ivory, amber, graphite), Cormorant Garamond для заголовков, Manrope для тела. Это работает как бренд.
- **Структура навигации** — понятное деление разделов (Обучение / События / Вакансии / Поставщики / Материалы). Breadcrumbs на всех внутренних страницах.
- **Дизайн-система** — design-tokens.json проработан: есть reference → system → component уровни, field-стейты, semantic-цвета. Компоненты (Button, EmptyState, ErrorState, LoadingState) имеют consistent API.
- **Тёмная тема** — на public-страницах реализована полноценная dark-тема с отдельным набором токенов.
- **Accessibility baseline** — кнопки имеют focus-visible ring, EmptyState/LoadingState/ErrorState используют role="status"/"alert", aria-busy.
- **Мобильная адаптивность** — layout не ломается на 375px, кнопки full-width, тач-таргеты ≥44px.

### Главные системные проблемы

1. **Перегруженная главная страница** — 8+ секций, нет фокуса, нет чёткого сценария.
2. **Слабая визуальная иерархия** — всё одинаковой значимости, трудно выделить главное.
3. **Нулевые счётчики на герое** — "0 ВАКАНСИИ | 0 ПОСТАВЩИКА | 0 МАТЕРИАЛОВ" в dark-теме вместо реальных данных.
4. **Неконсистентные фильтры** — на одних страницах фильтры развёрнуты, на других свёрнуты.
5. **CTA-кнопки конкурируют** — на каждом экране primary + secondary CTA без чёткого приоритета.
6. **Текстовая перегрузка заголовков** — слишком длинные H1 на многих страницах.
7. **Footer перегружен** — 4 колонки навигации, дублирующие хедер.

## 2. Screen-by-screen review

### 2.1 Главная страница (Hero)

**Проблема A: Нулевые счётчики в dark-теме**
- **Что не так:** На герое в dark-теме отображается "0 ВАКАНСИИ | 0 ПОСТАВЩИКА | 0 МАТЕРИАЛОВ". В light-теме видно реальные цифры (2/3/5). Это баг рендеринга — SSR-данные не доходят до dark-компонента, либо данные загружаются клиентски после гидрации.
- **Почему проблема:** Пользователь видит пустую платформу. Нулевые числа подрывают доверие к продукту с первой секунды.
- **Влияние:** Критичное — прямой bounce на первом экране.
- **Исправление:** Убедиться, что счётчики приходят из SSR и отображаются сразу. Если данных мало — показывать только ненулевые, или показывать общий текст без цифр.

**Проблема B: Два CTA одинаковой визуальной значимости**
- **Что не так:** "НАЙТИ ОБУЧЕНИЕ" (primary) и "СМОТРЕТЬ АФИШУ" (secondary/ghost) стоят рядом. Оба написаны UPPERCASE, оба занимают примерно равную визуальную площадь.
- **Почему проблема:** Пользователь не понимает, что главное действие. Два CTA на hero = ноль CTA.
- **Влияние:** Снижение конверсии первого клика.
- **Исправление:** Оставить один primary CTA. Второй — превратить в текстовую ссылку или убрать в навигацию.
- **Референс:** hero-секции Stripe, Linear, Notion — один яркий CTA + лёгкая текстовая ссылка. Агент должен сравнить результат с референсом и убедиться, что primary CTA визуально доминирует так же, как у референса — один чёткий акцент, без конкуренции.

**Проблема C: Поисковая строка на Hero перегружает**
- **Что не так:** Под двумя CTA — ещё и поисковая строка с кнопкой "Найти". Три уровня действий (CTA + CTA + search) на одном экране.
- **Почему проблема:** Когнитивная перегрузка. Пользователь должен решить: нажать кнопку? или искать?
- **Влияние:** Decision paralysis, особенно для новых пользователей.
- **Исправление:** Если поиск — основной паттерн (как у HH.ru), убрать кнопочные CTA и оставить только search. Если нет — убрать search с Hero, вынести в хедер или отдельный блок ниже.

### 2.2 Главная — секция "Обзор разделов" (карточки Обучение/Афиша/Вакансии/Материалы/Калькулятор/Поставщики)

**Проблема D: 6 одинаковых карточек без иерархии**
- **Что не так:** 6 карточек визуально идентичны: одинаковые иконки, одинаковый размер, одинаковый паттерн (иконка + badge + заголовок + описание + стрелка). Нет выделения самых важных.
- **Почему проблема:** Если всё важно — ничего не важно. Пользователь не знает, с чего начать.
- **Влияние:** Пользователь скроллит мимо, потому что не понимает, что выбрать.
- **Исправление:**
  1. Выделить 2-3 ключевых раздела визуально (больший размер карточки, иллюстрация, или акцентный цвет).
  2. Остальные показать как компактные ссылки.
  3. Или заменить на task-oriented блоки: "Я ищу работу", "Я ищу обучение", "Я ищу поставщика".
- **Референс:** Главная Behance, Dribbble — top-level навигация через 3-4 крупных визуальных блока + мелкие в футере. Агент должен сверить: основные 2-3 карточки заметно крупнее и ярче, остальные — компактный secondary-ряд. Если все карточки одного размера — это не как у референса.

### 2.3 Главная — секция "Выберите своё направление"

**Проблема E: Дублирование навигации**
- **Что не так:** Карточки ролей ("Я бариста", "Я поставщик зерна", "Я обжарщик или бренд") дублируют карточки разделов выше (Вакансии → для бариста, Поставщики → для поставщика).
- **Почему проблема:** Два разных навигационных паттерна для одних и тех же действий = путаница.
- **Влияние:** Пользователь прокрутил 2 экрана, но всё ещё не начал действовать.
- **Исправление:** Выбрать одну стратегию:
  - **A)** Role-based навигация (я бариста / я владелец / я поставщик) → убрать раздельные карточки.
  - **B)** Section-based навигация (Обучение / Вакансии / Поставщики) → убрать ролевые карточки.
  Не оба одновременно.

### 2.4 Главная — секция "Ближайшие события"

**Проблема F: Empty state для events показывает "Сейчас перерыв между сезонами"**
- **Что не так:** Вместо карточек событий — текстовый блок "Сейчас перерыв между сезонами". При этом рядом — карточки "Ближайшие встречи и события" как fallback.
- **Почему проблема:** Messaging некорректный — "перерыв между сезонами" звучит как "ничего не будет". Лучше сказать "Следующие события объявим в ближайшее время. Подпишитесь".
- **Влияние:** Пользователь уходит, потому что думает, что платформа неактивна.
- **Исправление:** Заменить текст на: "Готовим новые события. Подпишитесь, чтобы узнать первыми." + кнопка подписки/Telegram.

### 2.5 Главная — секции "Читать" и "Свежий контент"

**Проблема G: Дублирование контента**
- **Что не так:** Секция "Читать" показывает статью "Как считать себестоимость напитка". Ниже — карточки "Свежий контент" с теми же статьями и вакансиями.
- **Почему проблема:** Одна и та же статья появляется дважды на странице.
- **Влияние:** Ощущение бедности контента.
- **Исправление:** Объединить в одну секцию "Свежее на платформе" с карточками разных типов (статья + вакансия + поставщик).

### 2.6 Страница "Образование" (/education)

**Проблема H: Фильтры по ролям не работают как ожидается**
- **Что не так:** Кнопки "Все | Бариста | Менеджер | Владелец" выглядят как tabs, но фактически фильтруют один и тот же список. Когда все курсы — для бариста, фильтр "Менеджер" даёт пустоту без объяснения.
- **Почему проблема:** Пустой результат без empty state.
- **Влияние:** Менеджер/владелец думает, что для него ничего нет.
- **Исправление:** Показывать "Пока нет программ для менеджеров. Записаться на уведомление?" + кнопка.

**Проблема I: Длинный H1 — "Обучение для бариста и команд"**
- **Что не так:** Заголовок вместе с подзаголовком занимает 5 строк текста до первого полезного контента.
- **Почему проблема:** Слишком много текста до контента = slow time-to-value.
- **Влияние:** Мобильные пользователи скроллят полтора экрана до первого курса.
- **Исправление:** Сократить H1 до "Обучение". Подзаголовок — 1 строка. CTA — inline.

### 2.7 Страница "Афиша" (/events)

**Проблема J: Пустой результат при наличии фильтров**
- **Что не так:** Поиск + фильтры раскрыты, но результат — "Сейчас перерыв между сезонами". Ниже — fallback-карточки, которые выглядят как события, но не являются карточками событий.
- **Почему проблема:** Пользователь думает, что фильтры ничего не нашли, хотя на самом деле событий просто нет.
- **Влияние:** Путаница между "ничего не найдено" и "ничего нет".
- **Исправление:**
  1. Если событий нет вообще — скрыть фильтры, показать "Планируем новые события".
  2. Если события есть, но фильтр не нашёл — показать "По вашему запросу ничего не найдено. Попробуйте изменить фильтры."

### 2.8 Страница "Вакансии" (/vacancies)

**Проблема K: Фильтры развёрнуты по умолчанию — слишком много полей**
- **Что не так:** На mobile фильтры занимают 2 экрана (Поиск + Категория + Город + Формат + кнопка "Свернуть"). Пользователь не видит результаты без скролла.
- **Почему проблема:** Фильтры важнее результатов в визуальной иерархии.
- **Влияние:** На mobile пользователь видит только фильтры и уходит.
- **Исправление:** По умолчанию фильтры свёрнуты. Показывать только search-поле + кнопку "Фильтры". Раскрывать по нажатию. Хорошая новость: кнопка "СВЕРНУТЬ ФИЛЬТРЫ" уже есть — нужно просто инвертировать default state.
- **Референс:** HH.ru, Indeed — поиск видим сразу, фильтры в сайдбаре или за кнопкой. Агент должен сравнить: после исправления фильтры должны быть свёрнуты, виден только search + количество результатов + первая карточка вакансии — как на HH.ru.

**Проблема L: Карточка вакансии перегружена метаданными**
- **Что не так:** КАТЕГОРИЯ + ГОРОД + ДАТА + Заголовок + зарплата + ОПЫТ + ФОРМАТ + ГРАФИК + аватар компании + описание + 2 кнопки (Откликнуться / Подробнее). ~12 элементов на карточку.
- **Почему проблема:** Глаз не знает, куда смотреть. Нет чёткого scan-path.
- **Влияние:** Медленное сканирование списка.
- **Исправление:**
  1. Первый ряд: Заголовок + зарплата (крупно).
  2. Второй ряд: компания + город (мелко).
  3. Третий ряд: badges (формат, опыт) — компактно.
  4. Один CTA: "Подробнее" (Откликнуться — на детальной странице).

### 2.9 Страница "Поставщики" (/suppliers)

**Проблема M: Неконсистентность с вакансиями**
- **Что не так:** Фильтры раскрыты, но layout другой: labels другого стиля (Направление / Город работы / Статус vs Категория / Город / Формат).
- **Почему проблема:** Одинаковые по функции страницы выглядят по-разному.
- **Влияние:** Нарушение паттернов, дополнительная когнитивная нагрузка.
- **Исправление:** Унифицировать filter-layout: одна и та же FilterPanel-компонент на всех listing-страницах.

### 2.10 Страница "Материалы" (/articles)

**Проблема N: Нет визуальных изображений в карточках**
- **Что не так:** Карточки статей — чисто текстовые (badge + заголовок + описание + мета + ссылка). Нет обложек.
- **Почему проблема:** Статьи без изображений сканируются медленнее. Особенно на странице, где основной контент — контент.
- **Влияние:** Статьи выглядят как сухой список, а не как интересный контент.
- **Исправление:** Добавить thumbnail-изображение в карточку (хотя бы для featured-статей). Или использовать cover-image из article entity.

### 2.11 Страница "Контакты" (/contacts)

**Проблема O: Дублирование раздела "Способ связи"**
- **Что не так:** Сначала блок "Связь с командой" с Email + Telegram. Затем форма обращения, в которой тоже есть поля Email + Телефон + Telegram. Пользователь видит email дважды.
- **Почему проблема:** Непонятно, зачем указывать email в форме, если email команды уже виден.
- **Влияние:** Форма кажется избыточной.
- **Исправление:** Убрать промежуточный блок с контактами. Форма — primary action. Email/Telegram — как secondary option внизу формы с пометкой "Или напишите нам напрямую".

**Проблема P: Форма контактов — слишком много полей**
- **Что не так:** Имя + Тема (select) + Email + Телефон + Telegram + Сообщение + Согласие. 7 полей для контактной формы.
- **Почему проблема:** Каждое дополнительное поле снижает конверсию на 10-15%.
- **Влияние:** Пользователь уходит в Telegram вместо заполнения формы.
- **Исправление:** Минимальная форма: Имя + Контакт (один свободный input для email/телефона/tg) + Сообщение + Согласие. Тему можно подставлять из URL-параметра.

### 2.12 Страница "Для бизнеса" (/business)

**Проблема Q: Непонятное позиционирование**
- **Что не так:** Текст "Это не страница консалтинга и не заявка на разработку. Здесь команда принимает данные для карточки заведения в каталоге" — негативная формулировка.
- **Почему проблема:** Пользователь должен понять, чем страница НЕ является, чтобы понять, чем она является.
- **Влияние:** Путаница. "Это не то? Тогда где то?"
- **Исправление:** Позитивная формулировка: "Разместите ваше заведение в каталоге BARSYNERGY. Заполните карточку — мы проверим и опубликуем." Убрать отрицания.

### 2.13 Страница "Консалтинг" (/consulting)

**Проблема R: Заголовок секции "С какими задачами можно прийти" — слишком большой**
- **Что не так:** Текст display-шрифтом Cormorant Garamond занимает полэкрана с font-size ~72px.
- **Почему проблема:** Декоративный заголовок не несёт утилитарной функции и создаёт пустое пространство.
- **Влияние:** Контент уходит ниже fold, пользователь не видит конкретики.
- **Исправление:** Сократить заголовок, уменьшить размер до h2-product level (32px), добавить подзаголовок с конкретикой.

### 2.14 Страница "Калькулятор себестоимости" (/tools/cost-calculator)

**Проблема S: Отличный UX-инструмент, но с проблемами label'ов**
- **Что не так:** Поля "Ручная цена продажи, ₽" и "Доля себестоимости" — непонятны без контекста. Что такое "ручная цена"? Что значит число "30" в "Доля себестоимости"?
- **Почему проблема:** Бариста может не знать, что "доля себестоимости 30" = "30% от цены = себестоимость".
- **Влияние:** Ошибки в расчётах, недоверие к результату.
- **Исправление:**
  1. "Доля себестоимости" → "Целевая доля себестоимости, %" + hint "Обычно 25-35%. Если себестоимость занимает 30% от цены, остальное — ваша маржа."
  2. "Ручная цена продажи" → "Своя цена продажи" + hint "Если хотите задать цену вручную, а не считать по формуле."

### 2.15 Auth-флоу — Login (/auth/login)

**Проблема T: Role-selection на login-экране**
- **Что не так:** Перед полями Email/Пароль — выбор роли ("Я работаю в баре" / "Я владею заведением или представляю бренд"). Два карточных блока.
- **Почему проблема:** Выбор роли при логине — антипаттерн. Роль определяется при регистрации. При логине пользователь хочет быстро ввести credentials.
- **Влияние:** Дополнительный шаг перед вводом пароля = friction.
- **Исправление:** Убрать выбор роли с экрана логина. Оставить только Email + Пароль + "Войти" + ссылку на регистрацию. Роль — при регистрации.
- **Референс:** Login-экраны Linear, Notion, Figma — минимальная форма: email → пароль → кнопка. Без выбора ролей. Агент должен сверить: финальный login-экран должен быть такой же минималистичный — только поля ввода и одна кнопка.

### 2.16 Auth-флоу — Register (/auth/register)

**Проблема U: Слишком длинная форма регистрации**
- **Что не так:** Компания + Контактное лицо + Город + Email + Телефон + Telegram + Описание + Согласие. 8 полей.
- **Почему проблема:** Для первого контакта — слишком много. Пользователь не готов отдать столько данных незнакомому сервису.
- **Влияние:** Drop-off на регистрации.
- **Исправление:** Step 1: Email + Имя + Роль → Step 2 (после верификации): Компания + Город + Контакты. Разбить на 2 шага.

### 2.17 Admin Login (/admin)

**Проблема V: Минимальный, но без обратной связи**
- **Что не так:** Форма корректна (Почта + Пароль + Войти), но нет видимого error state на скриншоте. Placeholder дублирует label ("Почта" label + "Почта" placeholder).
- **Почему проблема:** Дублирование label/placeholder — визуальный шум. При фокусе label остаётся, placeholder исчезает — ок, но занимает место.
- **Влияние:** Мелкий, но системный вопрос — дублируется ли это на других формах?
- **Исправление:** Убрать placeholder если есть label. Или убрать label и оставить floating-label паттерн.

## 3. Системные UI/UX проблемы

### S1. Отсутствие единой стратегии навигации

**Проблема:** Хедер, hero-карточки, ролевые карточки, footer — четыре разных навигационных системы к одному и тому же контенту.

**Исправление:** Определить одну primary-навигацию (хедер) и одну discovery-навигацию (hero-секция или role-based). Убрать дублирование. Footer — только вспомогательные ссылки (правовые, контакты).

### S2. Неконсистентные фильтры на listing-страницах

**Проблема:** Вакансии, Поставщики, Статьи, События — у каждой свой layout фильтров. Где-то фильтры раскрыты, где-то свёрнуты. Где-то есть label "Фильтры", где-то нет. Разные label-стили (Категория vs Направление).

**Исправление:** Создать единый компонент `<ListingFilterPanel>`:
- Default state: свёрнуто (только search + кнопка "Фильтры").
- Раскрытый state: search + N select-полей + кнопка "Сбросить".
- Результат: "Найдено N" как chip.
- Одинаковый на всех listing-страницах.

### S3. CTA-конкуренция на каждом экране

**Проблема:** Почти на каждой странице — primary CTA (amber) + secondary CTA (outline). На Hero — 3 action-элемента.

**Исправление:** Правило: один primary CTA на экран/секцию. Вторая кнопка — ghost/link, визуально подчинённая. Audit каждой страницы:
- Hero: 1 primary CTA.
- Education: "Посмотреть форматы" → текстовая ссылка.
- Events: "Предложить событие" → secondary, не primary.
- Suppliers: "Добавить компанию" → secondary.
- Articles: "Предложить тему" → ghost.

### S4. Перегруженные заголовочные блоки (page headers)

**Проблема:** На каждой listing-странице: breadcrumb + label (uppercase) + H1 (display font) + subtitle (2-3 строки) + CTA. Занимает 300-400px высоты до контента.

**Исправление:** Compact page header: breadcrumb + H1 (одна строка, product font Manrope, не display) + CTA inline. Subtitle — только если несёт уникальную информацию. Экономия ~150px на каждой странице.
- **Референс:** Notion Help Center, Linear Docs — компактный заголовок в одну строку + CTA справа, без display-шрифтов на утилитарных страницах. Агент должен убедиться, что header-блок занимает не более 200px высоты (включая breadcrumb), заголовок — максимум 1 строка на desktop.

### S5. Отсутствие skeleton/loading для серверных компонентов

**Проблема:** LoadingState-компонент существует, но на listing-страницах при навигации нет промежуточного loading UI (Next.js loading.tsx). Пользователь видит либо пустоту, либо мгновенный переход.

**Исправление:** Добавить `loading.tsx` с skeleton-layout для каждой route-группы: `(public)/vacancies/loading.tsx`, `(public)/events/loading.tsx`, etc.

### S6. Empty states не предлагают следующее действие

**Проблема:** ContextualEmptyState имеет actionLabel/actionHref, но не все empty states их используют. "Сейчас перерыв между сезонами" — нет action.

**Исправление:** Каждый empty state должен предлагать действие:
- Нет вакансий → "Добавить вакансию" (для бизнеса) или "Подписаться на уведомления" (для бариста).
- Нет событий → "Предложить событие" или "Подписаться на анонсы".
- Нет результатов поиска → "Сбросить фильтры" или "Попробуйте другой запрос".

### S7. Тёмная тема на homepage не переключается

**Проблема:** Homepage hero и секция карточек остаются в dark-теме даже когда `data-theme=light`. Это by design (editorial dark zone), но создаёт путаницу: пользователь нажимает toggle — ничего не меняется на видимом экране.

**Исправление:** Либо hero должен реагировать на тему (light hero = ivory background + dark text), либо theme-toggle не должен показываться на homepage пока пользователь не проскроллит до light-секции.

## 7. Дополнительные находки (визуальный review)

### 7.1 Форма на /business — сломанная dark-тема в split-layout

**Скриншоты:** форма бизнес-заявки на /business в dark-теме

**Что не так:**
Форма `BusinessSolutionForm` имеет split-layout: левая панель (info) + правая панель (form fields). Левая панель использует `bg-[var(--graphite)]` + `text-white`, правая — наследует от `.editorial-form-shell`. В dark-теме:

1. **Левая панель:** `text-white/74` (opacity 74%) для bullet-текстов — недостаточный контраст на тёмном `var(--graphite)` (#171311). Визуально текст "смывается" и становится трудночитаемым.
2. **Общий контейнер** `.editorial-form-shell` в light-теме имеет cream-gradient (`rgba(255, 253, 249, 0.82)`), в dark-теме переключается на `var(--surface-elevated)`. Но при scroll или определённых viewport-размерах light-gradient может "просвечивать" через border-radius, создавая визуальный артефакт.
3. **Правая панель** (форма) — field labels и borders используют общие CSS-переменные, которые могут не адаптироваться к контексту `.editorial-form-shell` в dark-теме.

**Корневая причина:**
- `forms.css:1-11` — `.editorial-form-shell` имеет hardcoded light-mode gradient
- `forms.css:13-15` — dark-override использует `var(--surface-elevated)`, но потомки формы могут наследовать light-текстовые переменные из parent background-zone
- `business-solution-form.tsx:65` — `text-white/74` — слишком низкая opacity для body-текста

**Файлы для исправления:**
- `src/app/styles/forms.css` — строки 1-35 (editorial-form-shell + dark override)
- `src/components/public/business-solution-form.tsx` — строки 46, 65
- `src/components/public/application-form-section.tsx` — все EditorialShell usages

**Конкретное исправление:**

1. **Контраст текста в левой панели:** Заменить `text-white/74` → `text-white/85` для body-текста, `text-white/68` → `text-white/80` для мелких подписей. Минимальная opacity белого текста на `#171311` для AA-compliance — 0.78.

2. **Dark-theme form shell:** Убедиться, что `.editorial-form-shell` в dark-теме полностью перекрывает light-gradient:
   ```css
   :root[data-theme="dark"] .editorial-form-shell {
     background: var(--surface-elevated);
     /* Убрать все следы light-gradient */
     border-color: var(--border-subtle);
   }
   ```

3. **Проверить все формы с EditorialShell в dark-теме.** Затронутые компоненты:
   - `business-solution-form.tsx` — split-layout (/business)
   - `consulting-request-form.tsx` — (/consulting)
   - `supplier-application-form.tsx` — (/suppliers)
   - `partner-application-form.tsx` — (/partners)
   - `education-application-forms.tsx` — (/education)
   - `event-application-form.tsx` — (/events)
   - `contact-application-form.tsx` — (/contacts)
   - `vacancy-application-forms.tsx` — (/vacancies)

**Референс:** Формы Stripe Dashboard, Linear Settings — dark-theme формы имеют единый тёмный surface, чёткие border, белый текст без opacity-хаков. Агент: после исправления переключить тему на dark и пройти все 8 форм выше. На каждой форме текст должен быть чётко читаемым без прищуривания, contrast ratio ≥ 4.5:1. Если на любой форме текст "размывается" — исправление неполное.

### 7.3 Дублирование breadcrumb + eyebrow label на всех listing-страницах

**Скриншоты:** /events показывает "Главная > События" + "СОБЫТИЯ", /education — "Главная > Образование" + "ОБРАЗОВАНИЕ"

**Что не так:**
Компонент `EditorialPublicPage` (`src/components/public/editorial-public-page.tsx:113-114`) рендерит последовательно:
```tsx
<PublicBreadcrumbs current={breadcrumbLabel ?? eyebrow} />  // → "Главная > События"
<PublicEyebrow>{eyebrow}</PublicEyebrow>                     // → "СОБЫТИЯ"
```

Последний сегмент breadcrumb ("События") и eyebrow ("СОБЫТИЯ") — **один и тот же текст**, просто в разном регистре. Это visual noise: пользователь читает одно и то же слово дважды подряд.

**Масштаб проблемы:**
Компонент `EditorialPublicPage` используется на **12 страницах**:
- /education, /events, /vacancies, /suppliers, /articles, /business, /consulting, /partners, /search, /tools/cost-calculator, /contacts, /general-sponsors (через прямой вызов `PublicBreadcrumbs` + `PublicEyebrow`)

Плюс standalone-страницы (/about, /general-sponsors) которые напрямую используют тот же паттерн.

**Почему это проблема:**
- Визуальный шум — два элемента говорят одно и то же
- Занимают ~40-50px вертикального пространства впустую
- Ослабляют иерархию: breadcrumb теряет свою навигационную функцию, eyebrow теряет свою контекстную функцию

**Файлы для исправления:**
- `src/components/public/editorial-public-page.tsx` — строки 113-114 (compact), 132-133 (editorial)

**Конкретное исправление — два варианта:**

**Вариант A (рекомендуется): Убрать eyebrow, оставить breadcrumb**
Breadcrumb уже показывает где мы находимся. Eyebrow избыточен. Убрать `<PublicEyebrow>` из hero-секции, оставить только `<PublicBreadcrumbs>`. H1 идёт сразу после breadcrumb.

```tsx
// Было:
<PublicBreadcrumbs current={breadcrumbLabel ?? eyebrow} />
<PublicEyebrow className="mt-2" tone="muted">{eyebrow}</PublicEyebrow>
<PublicDisplayTitle as="h1" ...>{title}</PublicDisplayTitle>

// Стало:
<PublicBreadcrumbs current={breadcrumbLabel ?? eyebrow} />
<PublicDisplayTitle as="h1" className="mt-3" ...>{title}</PublicDisplayTitle>
```

Экономия: ~40px на каждой из 12+ страниц. Visually cleaner header.

**Вариант B: Убрать breadcrumb, оставить eyebrow**
Если eyebrow несёт бренд-функцию (uppercase label как стилистический элемент), убрать breadcrumb из hero и перенести его в sticky-header или сделать его invisible (aria-only для SEO).

**Рекомендация:** Вариант A — breadcrumb функциональнее, eyebrow — чисто декоративный дубль.

**Референс:** Notion Help, Stripe Docs, Linear Docs — все используют ЛИБО breadcrumb ЛИБО section label, но никогда оба. Агент: после исправления на каждой из 12 listing-страниц проверить, что между breadcrumb и H1 нет дублирующего текста. Ни один элемент не должен повторять текст из breadcrumb.
